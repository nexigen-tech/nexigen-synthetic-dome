# Proposal

## Why

The CAN generator and CAN monitor currently run as standalone processes with no orchestration. They connect directly to iceoryx2, bypassing the Composer layer entirely. This change creates a proper Composer-driven demo: a System Manifest describing the CAN pipeline, Composer validation, Dome Plan emission, and execution via `nexigen-run`. This serves as a reference for how any component or executable integrates with the Composer layer.

## What Changes

- **System Manifest** (`plans/composer-can-demo/manifest.json`): Declares the CAN source and CAN sink as component instances with their ports, partitions, wiring, and Chronos configuration.
- **Component descriptors**: Reuse existing `can_source.descriptor.json` and `can_sink.descriptor.json` (already generated by nxdc).
- **Composer validation**: Run `nxd_composer_manifest_test`-style validation on the manifest, verifying intra-partition wiring, source-name isolation, and descriptor matching.
- **Dome Plan emission**: Run the Composer's `emit_plan()` to produce a Dome Plan from the manifest.
- **nexigen-run execution**: Drive the CAN pipeline through one or more Chronos frames via `nexigen-run` with the emitted Dome Plan.
- **Documentation**: Full workflow from manifest → validation → emission → execution.

## Capabilities

### New Capabilities
- `composer/can-pipeline`: Composer-based orchestration of a CAN generator + CAN sink pipeline, covering manifest authoring, validation, plan emission, and execution through `nexigen-run`. Serves as a reference for integrating any component pair with the Composer.

### Modified Capabilities
None.

## Impact

- New directory `plans/composer-can-demo/` with manifest, emitted plan, and README.
- No changes to existing C++ or Rust code outside the new demo.
- Composer module (`nxd_composer`) is already compiled and tested.
