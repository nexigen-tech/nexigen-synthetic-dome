# Design

## Context

The Composer module (`runtime/composer/`) already validates System Manifests, emits Dome Plans, and is tested. The existing `can_source.descriptor.json` and `can_sink.descriptor.json` are generated by nxdc. The `nexigen-run` walking skeleton already demonstrates spawning processes from a Dome Plan.

See `specs/composer/can-pipeline/spec.md` for observable behaviour requirements.

## Goals / Non-Goals

**Goals:**
- A System Manifest at `plans/composer-can-demo/manifest.json` that describes the CAN pipeline
- A repeatable workflow: manifest → validate → emit → execute
- Documentation that external developers can follow

**Non-Goals:**
- No changes to the Composer, nexigen-run, or any existing module
- No ABI-1 plugin version of the CAN generator (standalone exec is fine)
- No multi-frame simulation or LET boundaries (single partition only)

## Decisions

### Decision: Manifest uses standalone executables, not ABI-1 plugins

The `nxd_can_generator` and `nxd_can_subscriber_helper` are standalone executables that manage their own iceoryx2 transport. They are declared in the manifest's `processes` section as executables, matching the pattern used by `nxd-ws01-echo` in the walking skeleton test.

The Composer's descriptor validation (`validate_against_descriptors`) checks that component instances declared in the manifest match the ports, contracts, and parameters in their `.descriptor.json` files. This check is independent of whether the process is an ABI-1 plugin or a standalone executable.

### Decision: Single partition, no LET boundary

Both instances (can_source, can_sink) share a single partition. The wire connecting them stays inside the partition, so no LET boundary is needed. This matches the simplest Composer-validated topology.

### Decision: Manually authored manifest, not programmatic

The manifest is hand-written as JSON, not generated by code. This makes it accessible as a reference for external developers. The Composer's `SystemManifest::from_json()` parses it.

## Risks / Trade-offs

- **Process lifecycle mismatch**: nexigen-run spawns processes via `posix_spawn` and sends SIGTERM. The CAN generator runs until SIGINT (Ctrl+C), not SIGTERM. The `nxd_can_subscriber_helper` runs until stdin closes. **Mitigation**: nexigen-run sends SIGTERM, which terminates both processes (SIGTERM kills without signal handler).
- **Descriptor-hash mismatch**: The `nxd_abi_entry()` in `can_source.cpp` uses a zeroed `descriptor_hash`. The Composer's descriptor validation compares against the hash in `can_source.descriptor.json`. **Mitigation**: Update the descriptor hash in the C++ source to match the nxdc-generated hash, or add `skip_descriptor_hash_check` to the manifest.
- **iceoryx2 service collision**: If the nexigen-run and the processes both try to create an iceoryx2 node with the same name, it may fail. **Mitigation**: The helper subscribes to the bus the generator publishes on — no collision.
